📋 Architecture Decision Records

ADR-001: Kafka Outbox

Accepted · 2026-05-31

Transactional Outbox pattern for reliable event publishing. Events written atomically with domain changes, async published via scheduler. At-least-once delivery with retry.

ADR-002: Strategy Pattern

Accepted · 2026-04-27

Strategy + Registry pattern for stock deduction. 4 interchangeable algorithms auto-registered via @Component. Type-safe EnumMap lookup per request.

ADR-003: Redis as Gate

Accepted · 2026-04-27

MySQL is durable source of truth; Redis is fast gate/cache. Compensation + reconciliation repair drift. 2.5× throughput over DB-only with zero oversell.

⚙️ Concurrency & Consistency

Core Invariants

dbStockAfter >= 0          oversoldCount = 0          dbOrderCount <= initialStock

For REDIS_LUA_WITH_COMPENSATION: redisStockAfter = dbStockAfter, driftAmount = 0.

UNSAFE_DB is intentionally allowed to violate these — it exists to make race conditions visible.

Strategy Comparison

StrategyOversell safetyRedis drift behavior
UNSAFE_DBnon/a
CONDITIONAL_DByesRedis may differ if warmed but unused
REDIS_LUAyes (normal)Can drift on DB/order failures
REDIS_LUA_WITH_COMPENSATIONyesRestores Redis on known failures
UNSAFE_DB
DB decrement without stock predicate. Race-condition baseline — overselling is expected evidence.
UPDATE ticket_item
SET stock_available = stock_available - :qty
WHERE id = :ticketItemId
CONDITIONAL_DB
Single atomic check-and-deduct. Zero affected rows = clean rejection.
UPDATE ticket_item
SET stock_available = stock_available - :qty
WHERE id = :id AND stock_available >= :qty
REDIS_LUA
Redis Lua gate first, then DB. Fast rejection, but no compensation on failure.
1. Lua decrement Redis atomically
2. Reject if Redis < quantity
3. DB conditional update
4. No restore on failure
REDIS_LUA + COMP
Redis Lua + DB + immediate restore. Preferred strategy for demos.
1. Lua decrement Redis
2. DB conditional update
3. Restore Redis if DB rejects
4. Compensation flag for order insert fail
5. Scheduled reconcile for double-fault

Reconciliation

1. Read Redis stock     4. If drift != 0, set Redis = DB
2. Read DB stock        5. Emit flashsale.reconciliation metric
3. drift = redis - db   6. Publish RECONCILIATION event via outbox → Kafka

Scheduled every 30s (10s initial delay) for default ticket item 4. Manual: POST /admin/benchmarks/reconcile.

Failure Semantics

Result codeMeaningRecovery
INVALID_REQUESTMissing/invalid request fieldFix request
REDIS_STOCK_UNAVAILABLERedis key missing or insufficientReset + warmup
DB_STOCK_DECREMENT_FAILEDDB conditional update rejectedCheck stock, strategy, consistency
ORDER_CREATE_FAILEDStock OK but insert failedCheck consistency, reconcile
WARMUP_FAILEDCould not read DB stockVerify fixture data

Reviewer Interpretation

  • UNSAFE_DB — overselling proves the race condition.
  • CONDITIONAL_DB — simplest DB-safe baseline.
  • REDIS_LUA — fast Redis gating, drift becomes visible.
  • REDIS_LUA_WITH_COMPENSATION — best demo: fast rejection + practical repair.
  • Throughput = local evidence; rerun on target machine before publishing claims.

Dưới đây là bộ 50 câu hỏi và trả lời phỏng vấn chuyên sâu được cấu trúc theo STAR Method (Situation, Task, Action, Result), giúp bạn hiểu rõ bối cảnh và giải pháp kỹ thuật thực tế trong dự án.

🏛️ Phần 1: Kiến trúc Hệ thống, Clean Architecture & DDD

1. DDD (Domain-Driven Design) là gì và tại sao dự án áp dụng mô hình phân lớp DDD?

Situation (S): Khi phát triển hệ thống bán vé flash sale chịu tải cao, nếu áp dụng kiến trúc 3 lớp truyền thống (Controller-Service-DAO), code nghiệp vụ đặt vé dễ bị trộn lẫn với mã nguồn hạ tầng cơ sở dữ liệu (MySQL/Redis), làm hệ thống cực kỳ khó nâng cấp, kiểm thử và tối ưu hóa hiệu năng độc lập.

Task (T): Cần thiết lập một cấu trúc dự án sạch, cô lập hoàn toàn logic nghiệp vụ lõi (Domain) khỏi các framework (Spring Boot) và các giải pháp lưu trữ hạ tầng.

Action (A): Triển khai mô hình phân lớp DDD chia dự án thành 5 module Maven: xxxx-domain (chứa thực thể thuần túy, các quy tắc bất biến, interface ports), xxxx-application (điều phối nghiệp vụ, transaction, registries), xxxx-infrastructure (triển khai các adapter cụ thể như MySQL JPA, Redis Cache, Kafka Outbox), xxxx-controller (HTTP REST APIs) và xxxx-start (entrypoint bootstrap).

Result (R): Module domain được giữ độc lập 100% với Spring Boot và JPA. Nhờ đó, việc viết unit test độc lập cực kỳ nhanh mà không cần khởi động database, đồng thời cho phép hoán đổi công nghệ lưu trữ hạ tầng mà không làm thay đổi hay hư hại mã nguồn nghiệp vụ lõi.

2. Sự khác biệt chính giữa Business Logic trong application module và domain module là gì?

Situation (S): Chức năng đặt vé flash sale đòi hỏi vừa phải kiểm tra các điều kiện nghiệp vụ (số lượng mua hợp lệ, tồn kho khả dụng) vừa phải xử lý các luồng công nghệ xung quanh (mở database transaction, ghi log sự kiện outbox, gửi tin nhắn đi Kafka).

Task (T): Phân định ranh giới trách nhiệm rõ ràng để tránh rò rỉ các logic điều phối hệ thống vào trong domain nghiệp vụ, ngăn chặn tình trạng "Anemic Domain Model".

Action (A): Thiết kế module domain chỉ quản lý quy tắc nghiệp vụ thuần túy không trạng thái ngoại lai (Invariants), ví dụ như kiểm tra số lượng vé khả dụng. Thiết kế module application làm lớp điều phối (Orchestrator), mở Transaction, gọi Repository Adapter, thực thi Registry Strategy để chọn chiến thuật trừ kho và gọi Outbox Service.

11. Hiện tượng Race Condition xảy ra thế nào trong luồng đặt vé? Vẽ luồng dẫn đến Oversell.

Situation (S): Dưới tải flash sale cực đại, hàng ngàn người dùng đặt vé cùng lúc dễ gây ra lỗi bán quá số lượng thực tế (Oversell).

Action (A): Mô tả luồng: Cả Thread A (User 1) và Thread B (User 2) cùng đọc tồn kho bằng 1, cùng thỏa mãn điều kiện stock >= 1 và cùng thực hiện trừ kho, dẫn đến bán được 2 vé trong khi thực tế chỉ có 1 vé khả dụng.

Result (R): Giúp đội ngũ phát triển nhận diện rõ lỗ hổng và chuyển hướng thiết kế sang các cơ chế đồng bộ nguyên tử (Atomic) ở tầng Database hoặc Cache.

12. Chiến lược "Unsafe DB" hoạt động thế nào và tại sao gây ra oversell trầm trọng?

Situation (S): Cần chạy thử nghiệm một kịch bản cơ bản để làm thước đo (baseline) cho hiện tượng oversell khi không áp dụng bất kỳ cơ chế khóa nào.

Task (T): Triển khai chiến lược UNSAFE_DB để chứng minh tác hại của Race Condition.

Action (A): Thực thi trực tiếp câu lệnh SQL cập nhật tồn kho: UPDATE ticket_item SET stock_available = stock_available - :qty WHERE id = :id mà không kiểm tra số tồn kho hiện tại đang âm hay dương.

Result (R): Stress test bằng JMeter ghi nhận oversoldCount = 4000 (tồn kho bị âm xuống -4000), chứng minh sự nguy hiểm của việc không kiểm soát đồng thời.

13. Làm thế nào chiến lược "Conditional DB Update" giải quyết được vấn đề oversell?

Situation (S): Sau khi thấy tác hại của UNSAFE_DB, chúng tôi cần một giải pháp bảo vệ tồn kho ngay tại tầng dữ liệu MySQL mà không làm nghẽn cổ chai luồng xử lý do dùng khóa bi quan.

Task (T): Triển khai cơ chế khóa lạc quan ngầm định thông qua câu lệnh SQL nguyên tử (Atomic Update).

Action (A): Thêm điều kiện lọc vào câu lệnh cập nhật tồn kho: UPDATE ticket_item SET stock_available = stock_available - :qty WHERE id = :id AND stock_available >= :qty.

Result (R): Nhờ cơ chế khóa dòng (Row-level Lock) của InnoDB, MySQL đảm bảo việc kiểm tra và cập nhật diễn ra nguyên tử. Kết quả đạt oversoldCount = 0 tuyệt đối, nhưng thông lượng chỉ đạt 173 req/sec do ghi đĩa trực tiếp.

Action (A): Đánh giá kỹ thuật: Khóa bi quan gây nghẽn luồng xử lý nghiêm trọng và cạn kiệt connection pool; Khóa lạc quan gây rollback liên tục do xung đột ghi lớn, làm quá tải CPU máy chủ.

Result (R): Loại bỏ cả hai phương pháp và thay thế bằng cơ chế kiểm tra nhanh ở cache Redis (Lua Script) để đạt hiệu năng cao nhất.

Action (A): Thiết lập cơ chế gửi lại: Worker quét các sự kiện vẫn ở trạng thái PENDING hoặc FAILED sau một khoảng thời gian chờ (10 giây) và tiến hành gửi lại sang Kafka (tối đa 5 lần).

Result (R): Đảm bảo sự kiện chắc chắn được gửi đến Kafka ít nhất một lần. Các hệ thống tiêu thụ (Consumer) phía sau chỉ cần triển khai cơ chế lọc trùng (Idempotent Consumer) dựa trên mã đơn hàng.

Result (R): Kafka đảm bảo tất cả tin nhắn có chung Message Key sẽ luôn được định tuyến vào cùng một phân vùng duy nhất (Partition) của topic và được tiêu thụ theo đúng thứ tự FIFO.

45. Đánh đổi về mặt thời gian (Latency) khi sử dụng Transactional Outbox là gì?

Situation (S): Gửi tin nhắn trực tiếp sang Kafka có độ trễ cực thấp nhưng kém an toàn. Chuyển sang dùng Outbox đảm bảo an toàn giao dịch nhưng có thể tạo độ trễ truyền tin nhắn.

Action (A): Hệ thống chấp nhận đánh đổi tính Nhất quán thời gian thực (Strong Consistency) lấy tính Nhất quán sau cùng (Eventual Consistency), điều chỉnh scheduler quét bảng outbox chạy mỗi 1 giây.

Result (R): Tốc độ phản hồi API đặt vé HTTP giảm xuống tối thiểu (vì không phải chờ kết nối Kafka), đổi lại tin nhắn sẽ đến Kafka chậm hơn khoảng 0.5 - 1 giây. Đây là mức đánh đổi hoàn toàn chấp nhận được trong hệ thống thương mại điện tử.

50. Nếu cần mở rộng hệ thống đáp ứng lượng traffic gấp 10 lần, bạn sẽ đề xuất gì?

51. Cơ chế hoạt động của @Transactional trong Spring và tại sao nó không hoạt động khi tự gọi (self-invocation)?

Situation (S): Trong ứng dụng Spring Boot, chúng tôi sử dụng annotation @Transactional để quản lý giao dịch database. Một lỗi phổ biến là khi viết một phương thức không có transaction gọi một phương thức có transaction trong cùng một class, giao dịch không hề được mở và dữ liệu không rollback khi gặp sự cố.

Task (T): Giải thích cơ chế proxy đứng sau @Transactional và cách khắc phục lỗi tự gọi (self-invocation).

Action (A): Giải thích rằng Spring bọc Bean bằng một Dynamic Proxy để đánh chặn cuộc gọi và quản lý transaction (mở/commit/rollback). Khi tự gọi nội bộ trong cùng một class, cuộc gọi không đi qua proxy mà đi trực tiếp vào method thực tế. Khắc phục bằng cách: (1) Tách logic sang Bean khác; (2) Tự inject chính Bean đó bằng @Autowired + @Lazy; (3) Sử dụng AopContext.currentProxy().

Result (R): Đảm bảo 100% các giao dịch ghi đơn hàng và outbox event được bọc đúng proxy, loại bỏ hoàn toàn các trường hợp không rollback dữ liệu do lỗi cấu hình transaction.

52. Sự khác biệt giữa Transaction Propagation REQUIRED và REQUIRES_NEW? Ứng dụng thế nào?

Situation (S): Khi đặt vé, hệ thống cần ghi log hành trình giao dịch của người dùng. Nếu việc ghi log giao dịch phụ thất bại làm rollback luôn cả đơn đặt vé thành công của khách hàng, đó là một lỗi nghiệp vụ nghiêm trọng.

Task (T): Phân định ranh giới transaction của luồng chính (đặt vé) và luồng phụ (ghi log/outbox) bằng cơ chế lan truyền transaction (Propagation).

Action (A): Cấu hình luồng chính đặt vé dùng propagation REQUIRED (sử dụng transaction hiện tại nếu có, tạo mới nếu chưa). Cấu hình luồng ghi log audit dùng propagation REQUIRES_NEW (luôn tạo transaction mới độc lập, tạm dừng transaction hiện tại).

Result (R): Đơn đặt vé chính vẫn được tạo thành công ngay cả khi hệ thống ghi log audit gặp lỗi và bị rollback, tăng độ tin cậy của giao dịch lên mức tối đa.

53. Cách giải quyết các hiện tượng tranh chấp dữ liệu (Dirty Read, Non-repeatable Read, Phantom Read) ở mức database Isolation Levels?

Situation (S): Dưới áp lực truy cập đồng thời của flash sale, nhiều transaction đọc và ghi tồn kho chạy song song. Nếu không thiết lập mức độ cô lập (Isolation Level) phù hợp, các transaction đọc sẽ thấy dữ liệu tạm thời chưa commit hoặc bị thay đổi giữa chừng, dẫn đến tính toán sai tồn kho.

Task (T): Lựa chọn và cấu hình mức độ cô lập tối ưu giữa tính toàn vẹn dữ liệu và hiệu năng ghi của MySQL.

Action (A): Sử dụng mức cô lập mặc định của InnoDB là REPEATABLE READ. Mức này sử dụng kỹ thuật MVCC (Multi-Version Concurrency Control) và Next-Key Locks để ngăn chặn hoàn toàn Dirty Read và Non-repeatable Read, đồng thời chống Phantom Read mà không cần nâng lên mức SERIALIZABLE quá chậm.

Result (R): Đảm bảo các luồng đọc tồn kho để đối soát dữ liệu luôn nhận được kết quả nhất quán trên mọi truy vấn, bảo vệ tính toàn vẹn dữ liệu với hiệu năng ghi tối đa.

54. Cơ chế MySQL Replication (Master-Slave) hoạt động thế nào và cách xử lý lỗi trễ đồng bộ (Replication Lag)?

Situation (S): Để tăng khả năng chịu tải, chúng tôi thiết lập cụm DB gồm 1 node Master (chuyên ghi) và các node Slaves (chuyên đọc). Khi người dùng vừa đặt vé thành công (ghi Master) và lập tức chuyển sang trang lịch sử đơn hàng (đọc Slave), nếu Slave chưa kịp đồng bộ dữ liệu (Replication Lag), người dùng sẽ không thấy đơn hàng mới của mình.

Task (T): Thiết kế giải pháp phân phối đọc/ghi đảm bảo trải nghiệm người dùng không bị ảnh hưởng bởi độ trễ đồng bộ.

Action (A): Áp dụng các giải pháp: (1) Pin to Master: Sau khi ghi Master, bắt buộc các yêu cầu đọc thông tin đơn hàng của người dùng đó phải định tuyến thẳng về Master trong vài giây đầu; (2) Sử dụng Semi-synchronous Replication đảm bảo ít nhất 1 node Slave đã nhận được binlog trước khi Master phản hồi thành công.

Result (R): Loại bỏ hoàn toàn lỗi hiển thị thiếu thông tin sau khi mua vé, đảm bảo trải nghiệm người dùng mượt mà trong khi vẫn tận dụng được sức mạnh đọc song song của cụm Slave.

55. Virtual Threads (Java 21) hoạt động thế nào? Sự khác biệt với Platform Thread và hiện tượng Pinning là gì?

Situation (S): Thread truyền thống của Java (Platform Thread) ánh xạ 1-1 với Kernel Thread của hệ điều hành, tiêu tốn khoảng 1MB RAM mỗi thread. Khi có 5000 request đồng thời, việc tạo quá nhiều thread sẽ làm sập bộ nhớ máy chủ.

Task (T): Tăng khả năng xử lý đồng thời lên gấp nhiều lần mà không cần viết code reactive phức tạp.

Action (A): Bật tính năng Virtual Threads trên Spring Boot 3.3.5 (Java 21). Ánh xạ hàng vạn Virtual Threads (chỉ vài KB) lên một số lượng nhỏ Carrier Threads (Platform Threads chạy trên CPU cores). Tránh hiện tượng Pinning bằng cách thay thế các khối lệnh synchronized bằng ReentrantLock để không block Carrier Thread khi chạy I/O.

Result (R): Hệ thống xử lý mượt mà 5000 requests đồng thời chỉ với tài nguyên RAM cực kỳ nhỏ, thông lượng cải thiện rõ rệt mà vẫn giữ nguyên mô hình lập trình đồng bộ (imperative code) trực quan.

56. So sánh cơ chế CAS (Compare-And-Swap) của AtomicInteger với block synchronized truyền thống trong Java?

Situation (S): Khi cần tăng/giảm một biến đếm toàn cục (như số lượng request thành công) song song trên bộ nhớ, việc dùng block synchronized sẽ ép các thread phải xếp hàng chờ đợi, làm giảm đáng kể hiệu năng CPU.

Task (T): Thực hiện cập nhật biến đếm nguyên tử với hiệu năng cao nhất dưới tải lớn.

Action (A): Sử dụng các lớp Atomic (như AtomicInteger, LongAdder) chạy trên cơ chế CAS (Compare-And-Swap) ở mức phần cứng CPU (không sử dụng lock ở mức OS). Thread sẽ đọc giá trị, tính toán giá trị mới, và gửi lệnh CPU so sánh và ghi đè giá trị nếu trùng khớp giá trị cũ; nếu khác, lặp lại vòng thử (spin loop).

Result (R): Thông lượng cập nhật biến đếm tăng gấp 5-10 lần so với sử dụng synchronized, giúp giảm tải tranh chấp thread trên CPU và loại bỏ nguy cơ nghẽn luồng.

57. Hiện tượng Consumer Rebalance trong Kafka là gì? Làm thế nào để giảm thiểu ảnh hưởng của nó?

Situation (S): Khi consumer group đang tiêu thụ sự kiện đơn hàng, nếu có một consumer node mới tham gia hoặc node cũ bị sập (hoặc xử lý quá lâu gây timeout), Kafka sẽ kích hoạt tiến trình Rebalance để chia lại partition. Trong lúc Rebalance diễn ra, toàn bộ việc tiêu thụ sự kiện bị đóng băng, gây tắc nghẽn tin nhắn.

Task (T): Tối ưu hóa cấu hình consumer để giảm tần suất và tác động của tiến trình Rebalance.

Action (A): Thực hiện cấu hình các tham số consumer: Tăng max.poll.interval.ms (lên 5 phút) để tránh consumer bị coi là chết khi đang xử lý lô đơn hàng lớn, điều chỉnh session.timeout.ms hợp lý, và áp dụng phân chia partition tĩnh (Static Membership) bằng cách cấu hình group.instance.id.

Result (R): Thời gian đóng băng hệ thống do Rebalance giảm từ vài phút xuống gần như bằng 0, đảm bảo luồng xử lý sự kiện đặt vé từ Kafka luôn trơn tru và liên tục.

58. Làm thế nào Kafka đảm bảo Exactly-Once Semantics (EOS)?

Situation (S): Trong luồng xuất bản sự kiện nghiệp vụ sang Kafka, nếu chỉ sử dụng At-least-once, lỗi mạng hoặc gửi lại tin nhắn từ Outbox worker có thể gây trùng lặp sự kiện, dẫn tới việc xử lý nghiệp vụ sai ở Consumer (ví dụ: trừ tiền khách hàng 2 lần).

Task (T): Thiết lập cơ chế gửi tin nhắn Exactly-Once nguyên tử trên toàn bộ luồng truyền tin.

Action (A): Cấu hình Idempotent Producer (enable.idempotence=true) để Kafka gán ID duy nhất cho từng lô tin nhắn và lọc trùng ở broker. Đồng thời sử dụng giao dịch Kafka (Kafka Transactions) bọc các hoạt động đọc-xử lý-ghi của consumer bằng cách cấu hình processing.guarantee=exactly_once_v2.

Result (R): Đảm bảo mỗi sự kiện đơn hàng chỉ được lưu và xử lý đúng một lần duy nhất trên toàn bộ hệ thống phân tán, loại bỏ hoàn toàn các lỗi nghiệp vụ do trùng lặp tin nhắn.

59. Cách thiết kế Dead Letter Topic (DLT) và retry policy trong Kafka Consumer khi gặp sự cố nghiệp vụ?

Situation (S): Khi consumer nhận một sự kiện đặt vé để xử lý, nếu gặp sự cố mạng tạm thời hoặc lỗi dữ liệu không hợp lệ, việc consumer liên tục thử lại ngay trên luồng chính sẽ gây nghẽn toàn bộ partition đó.

Task (T): Thiết kế cơ chế xử lý lỗi không đồng bộ giúp cô lập tin nhắn lỗi mà không ảnh hưởng đến các tin nhắn bình thường khác.

Action (A): Thiết lập kiến trúc Retry & DLT: Khi xử lý tin nhắn gặp lỗi tạm thời (Transient Error), gửi tin nhắn đó sang một Retry Topic kèm cấu hình trễ (Backoff Delay) để xử lý lại sau. Nếu thử lại quá số lần quy định hoặc gặp lỗi nghiệp vụ không thể sửa (Non-retryable Error), gửi tin nhắn đó sang Dead Letter Topic (DLT) để kiểm tra thủ công, đồng thời commit offset tin nhắn gốc trên topic chính để tiếp tục luồng.

Result (R): Ngăn chặn hoàn toàn hiện tượng nghẽn partition do lỗi của một vài tin nhắn cá biệt, đảm bảo hệ thống luôn hoạt động liên tục và các lỗi được ghi nhận đầy đủ để xử lý sau.

60. Cách triển khai Distributed Rate Limiting chống tấn công DDoS ở tầng Gateway bằng Redis?

Situation (S): Trong các chiến dịch flash sale, hàng triệu bot hoặc kẻ xấu có thể gửi hàng loạt request rác liên tục để làm sập hệ thống đặt vé. Một giải pháp Rate Limit cục bộ trên từng node Spring Boot là không đủ vì không chia sẻ được trạng thái giới hạn giữa các node trong cụm.

Task (T): Thiết kế cơ chế giới hạn tần suất truy cập phân tán (Distributed Rate Limiting) dùng chung cho toàn bộ cụm server.

Action (A): Triển khai thuật toán Token Bucket hoặc Sliding Window Log sử dụng Redis và Lua Script tại tầng API Gateway (Nginx hoặc Spring Cloud Gateway). Mỗi request gửi đến sẽ gọi script Lua để kiểm tra và giảm số lượng token hiện tại của IP/User trong Redis. Nếu hết token, lập tức trả về mã HTTP 429 Too Many Requests.

Result (R): Ngăn chặn hiệu quả 100% các đợt càn quét của bot rác, bảo vệ tài nguyên tính toán của backend Spring Boot chỉ dành cho người dùng thực tế và duy trì tính ổn định của hệ thống.

61. Làm thế nào để triển khai Distributed Tracing giám sát luồng đi của request qua các microservices?

Situation (S): Khi chuyển dịch sang kiến trúc microservices (Order, Payment, Notification Service), việc debug lỗi hoặc tìm nguyên nhân gây chậm request trở nên cực kỳ khó khăn vì log bị phân mảnh ở nhiều máy chủ khác nhau.

Task (T): Thiết lập hệ thống giám sát hành trình request xuyên suốt qua toàn bộ các service phân tán.

Action (A): Tích hợp thư viện OpenTelemetry vào các service. Khi một request đi vào API Gateway, hệ thống tự động sinh một Trace ID duy nhất. ID này được đính kèm vào HTTP Header (theo chuẩn W3C traceparent) và truyền qua các lệnh gọi REST API hoặc chèn vào metadata của Kafka message. Tất cả log ghi nhận đều được cấu hình in kèm Trace ID này và đẩy về Jaeger/Zipkin.

Result (R): Quản trị viên chỉ cần tìm kiếm theo Trace ID trên giao diện Jaeger là có thể nhìn thấy toàn bộ sơ đồ thời gian phản hồi (Gantt Chart) của request qua từng service, giúp định vị chính xác vị trí lỗi hoặc nút thắt cổ chai chỉ trong vài giây.
